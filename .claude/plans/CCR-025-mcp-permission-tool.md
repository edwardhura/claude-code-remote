# Plan: CCR-025 — MCP permission-prompt-tool integration

## Goal

Wake the dormant CCR-024 permission scaffolding against the channel Claude
actually uses for non-interactive permission gating: an MCP server that
exposes one tool (`ccr_permission_prompt`) which Claude invokes whenever it
needs the user's approval for a tool call. The MCP server runs **in-process**
on the same asyncio loop as the bot and (eventually) the web server, talks to
Claude over **stdio** via a small relay subprocess that `ClaudeProcess`
spawns alongside the claude binary, and resolves each invocation against an
asyncio.Future keyed on a manager-minted `request_id`. Tapping a Telegram
button calls `SessionManager.resolve_permission(request_id, decision)`,
which sets the Future, which lets the MCP tool return
`{"behavior": "allow", "updatedInput": ...}` or `{"behavior": "deny",
"message": ...}` to Claude, unblocking the original tool call.

After this ticket lands, a real `python -m ccr serve` session with
`PROMPT_TOOL=ccr_permission_prompt` wired into claude's argv surfaces inline
buttons in Telegram on the first permission-requiring tool, and a tap is
honoured end-to-end.

### `src/ccr/claude/mcp.py` — in-process server

```python
# Sketch — illustrative, not the final code.
class McpPermissionServer:
    """In-process MCP server exposing one tool: ccr_permission_prompt.

    Lifecycle: start() spawns a tiny relay subprocess that proxies stdio
    to/from the in-process Server via a memory stream pair, writes a
    temp .mcp.json config file so claude can discover us, and returns.
    stop() closes the stream pair, terminates the relay, and resolves all
    outstanding Futures with a deny payload.
    """

    def __init__(
        self,
        *,
        bus: EventBus,
        timeout_seconds: float = 120.0,
    ) -> None: ...

    async def start(self) -> None: ...
    async def stop(self) -> None: ...

    @property
    def claude_argv(self) -> list[str]:
        """Tokens to splice into claude's argv (after our control flags,
        before claude_extra_args)."""
        # Returns: ["--permission-prompt-tool",
        #          "mcp__ccr__ccr_permission_prompt",
        #          "--mcp-config", str(self._config_path)]
        ...

    # --- bot-facing ---
    def is_pending(self, request_id: str) -> bool: ...
    async def resolve(
        self,
        request_id: str,
        decision: dict[str, Any],
    ) -> bool:
        """Set the Future. Returns False if request_id was already resolved
        or never registered."""
        ...

    async def cancel_pending(self, session_id: uuid.UUID) -> int:
        """Resolve every outstanding Future for ``session_id`` with a deny.
        Returns the number cancelled."""
        ...

    # --- internal: invoked via the MCP tool dispatch ---
    async def _on_tool_call(
        self,
        tool_name: str,
        tool_input: dict[str, Any],
    ) -> dict[str, Any]:
        """Mint a request_id, register a Future, publish to the bus,
        await the Future (with timeout), return the decision payload."""
        ...
```

### `src/ccr/claude/manager.py` — added surface

```python
# Sketch — illustrative, not the final code.
class SessionManager:
    def __init__(self, *, bus, db_factory, settings) -> None:
        ...
        self._mcp = McpPermissionServer(
            bus=bus,
            timeout_seconds=settings.mcp_permission_timeout_seconds,
        )
        self._mcp_started = False

    async def resolve_permission(
        self,
        request_id: str,
        decision: dict[str, Any],
    ) -> bool:
        """Forward to the MCP server. Returns True if the Future was set
        by THIS call, False if the request_id was unknown or already
        resolved (the bot maps both to "Stale prompt")."""
        return await self._mcp.resolve(request_id, decision)

    def is_permission_pending(self, request_id: str) -> bool:
        return self._mcp.is_pending(request_id)

    # In new_session() / continue_session(), before constructing
    # ClaudeProcess:
    if not self._mcp_started:
        await self._mcp.start()
        self._mcp_started = True

    # In _teardown_locked():
    if session_id is not None:
        await self._mcp.cancel_pending(session_id)
```

### `src/ccr/bot/handlers/permission.py` — real handler body

```python
# Sketch — illustrative.
@router.callback_query(F.data.startswith("perm:"))
async def cb_permission(
    cb: CallbackQuery,
    session_manager: SessionManager,
    is_paired_user: bool,
) -> None:
    if not is_paired_user:
        await cb.answer("Not paired.", show_alert=True)
        return
    if cb.data is None or cb.from_user is None:
        return
    parsed = _parse_callback(cb.data)
    if parsed is None:
        await cb.answer("Stale prompt", show_alert=True)
        return
    _session_id, request_id, choice = parsed

    if choice not in ("approve", "deny"):
        await cb.answer("Stale prompt", show_alert=True)
        return

    decision = (
        {"behavior": "allow", "updatedInput": None}
        if choice == "approve"
        else {"behavior": "deny", "message": "Denied by user"}
    )
    resolved = await session_manager.resolve_permission(request_id, decision)
    if not resolved:
        await cb.answer("Stale prompt", show_alert=True)
        return

    username = cb.from_user.username or str(cb.from_user.id)
    suffix = f"\n→ {html.escape(choice)} (by @{html.escape(username)})"
    if cb.message is not None:
        original = cb.message.html_text or cb.message.text or ""
        with contextlib.suppress(TelegramBadRequest):
            await cb.message.edit_text(original + suffix, reply_markup=None)
    await cb.answer()
```

## Patterns and prior art

- **Reuse — keyboard:** `src/ccr/bot/keyboards.py:33-59` `permission_kb` is
  preserved verbatim from CCR-009/CCR-024. The new envelope feeds it the
  same `(session_id, request_id, options)` triple.
- **Reuse — callback parser:** `src/ccr/bot/handlers/permission.py:30-49`
  `_parse_callback` is reused verbatim. The handler body comes back; the
  parse helper does not change.
- **Reuse — bus payload shape:** `src/ccr/server.py:103-113` already pulls
  `event` and `session_id` out of the `session.event` payload. Same shape
  carries `McpPermissionRequest`; the broadcast loop just adds an
  `isinstance(event, McpPermissionRequest)` branch in
  `_materialise_keyboards`.
- **Reuse — sentinel-then-materialise:** the `_PendingKeyboard` pattern
  documented in the CCR-009 plan
  (`.claude/plans/CCR-009-permission-buttons.md` "Where does the keyboard's
  session_id come from") is the right shape here too. The formatter is a
  pure function of the event; the broadcast loop owns the `session_id` and
  swaps the sentinel for an `InlineKeyboardMarkup`. Re-introduce the same
  helpers (`_PendingKeyboard` private to `formatting.py`,
  `_materialise_keyboards` in `server.py`) — the same code that was
  removed in CCR-024 with the same shape, just driven by the new envelope.
- **Reuse — `ClaudeProcess` argv ordering:** `src/ccr/claude/process.py:84-101`
  carefully orders our control flags first, then `--continue` /
  `--resume`, then `claude_extra_args`. The MCP flags slot in immediately
  before `claude_extra_args` so the user can still override them by
  appending — same precedent as `--continue`.
- **Reuse — session-lock locality:** `src/ccr/claude/manager.py:174-249`
  `new_session` holds `_session_lock` for the full transition. The MCP
  start (lazy, idempotent) lives **before** the `ClaudeProcess.start()`
  call inside the lock, so concurrent `new_session` calls cannot both spawn
  the relay subprocess. Same lock guards `_teardown_locked`'s
  `cancel_pending(session_id)` call so an in-flight tap cannot race a
  shutdown.
- **Reuse — short-lived DB writes / fire-and-forget pattern:** none of the
  new state hits SQL. The Future map is in-memory only. This matches
  `CLAUDE.md`'s "JSONL events are not in SQL" architecture.
- **Reuse — `tests/fakes/fake_claude.py`:** stays a JSONL-only fake. The
  new MCP-protocol tests use a separate in-memory MCP client driver that
  speaks directly to `McpPermissionServer` over an in-process stream pair;
  no real Claude binary, no real subprocess, no stdio relay needed for
  unit tests.
- **Avoid — out-of-process MCP server.** Spawning a separate Python
  process to host the server adds a second lifecycle the manager has to
  babysit (start, supervise, restart on crash, propagate signals) for no
  architectural benefit. Modular monolith on one asyncio loop says
  in-process. (See "Decisions / In-process".)
- **Avoid — TCP transport.** Opens a port we then have to allowlist /
  document / firewall. stdio is what claude documents for local MCP tools
  and matches the trust boundary (claude already lives in our process
  tree). (See "Decisions / Transport".)
- **Avoid — re-introducing the CCR-009 pause/buffer.** With per-request
  Futures, multiple concurrent permission requests do not need a
  Telegram-side pause: each one has its own keyboard. (See
  "Decisions / Concurrency".)
- **Avoid — tracking which Telegram user answered in SQL.** The
  `edit_text` suffix already records the username; that is sufficient
  audit. Same call as CCR-009.

## Abstractions

**One new long-lived abstraction: `McpPermissionServer`.** Justified: this
ticket already produces three concrete callers — `SessionManager.__init__`
(lifecycle owner), `ClaudeProcess.__init__` (consumes `claude_argv`), and
`SessionManager.resolve_permission` (forwards to `resolve`). Plus a fourth
in tests. The server class encapsulates four pieces of state (Future map,
relay subprocess handle, temp config file path, MCP `Server` instance) and
their lifecycles; folding all four into `SessionManager` would balloon
that class and entangle two unrelated concerns (claude subprocess
management vs. MCP-protocol bookkeeping). The new class lives in its own
module so its public surface is small and documented.

**No abstraction over the Future-keying scheme.** A
`dict[str, asyncio.Future[dict[str, Any]]]` plus a
`dict[str, uuid.UUID]` (request_id → session_id, used only by
`cancel_pending`) is the right size. We do not introduce a `PermissionGate`
class, a `RequestRegistry`, or per-session sub-objects. Three concrete
callers (`_on_tool_call`, `resolve`, `cancel_pending`) are not enough to
justify a class around two dicts.

**No abstraction over the bus envelope.** `McpPermissionRequest` is a
plain Pydantic `BaseModel` (not a member of the discriminated `ClaudeEvent`
union), and the bus payload still uses the existing
`{"session_id", "seq", "event"}` shape — `event` is just typed
`ClaudeEvent | McpPermissionRequest` from the consumer's point of view.
This is the smallest possible widening.

## Edge cases the developer must handle

- **MCP server lifecycle vs. session lifecycle.** The server is
  manager-scoped, not session-scoped. `start()` runs once on the first
  `new_session` / `continue_session` call (idempotent guard); `stop()`
  runs in `serve()`'s `finally` block. Rationale: claude's `--mcp-config`
  flag points at a fixed file path, and the MCP `Server` instance can
  outlive any single claude subprocess — re-using it across sessions
  avoids spinning up a relay subprocess and rewriting a temp file every
  `/clear`.
- **Idempotent `start()`.** Concurrent first-session callers must not
  race the relay-subprocess spawn. The session lock around `new_session`
  serialises this naturally; the `start()` method also has its own
  internal `_started` guard for defence in depth.
- **Timeout policy.** `_on_tool_call` does
  `await asyncio.wait_for(future, timeout=settings.mcp_permission_timeout_seconds)`
  (default 120 s). On timeout: resolve the Future internally with a
  `{"behavior": "deny", "message": "Timed out — no paired user
  responded within {N}s"}` payload, log a structured WARN, return that
  payload to claude. The bot does NOT see a stale message — the
  user-facing keyboard simply stops working and a subsequent tap maps to
  "Stale prompt" via `is_pending() == False`. (Out-of-scope niceties:
  editing the message to "Timed out" on timeout — could be added later
  by having the MCP server publish a `permission.timeout` envelope; not
  in this ticket.) Default chosen: 120 s. Rationale: long enough that a
  user opening Telegram after a meeting still has the keyboard live;
  short enough that a forgotten session does not hang claude forever.
- **Default-deny on timeout / cancel.** Both timeout and
  session-teardown cancel produce the same `{"behavior": "deny", ...}`
  payload. This is the safest fail-closed behavior for permission
  gating.
- **Multiple simultaneous tool calls (parallel tool use in one turn).**
  Trivially supported: each call mints its own `request_id` and Future.
  Each gets its own envelope on the bus, its own broadcast message, its
  own keyboard. Users can tap them in any order. No global pause flag,
  no counter, no buffer. (See "Decisions / Concurrency".)
- **`resolve_permission` for an unknown / already-resolved
  `request_id`.** `McpPermissionServer.resolve` returns `False`. The
  handler maps that to `cb.answer("Stale prompt", show_alert=True)` and
  does NOT edit the message (the user who tapped first has already
  edited it, or the request was timed-out). Same UX as the CCR-009 stale
  branch.
- **Concurrent taps from two paired users on the same prompt.** The
  Future is single-shot; only the first `Future.set_result(...)` wins
  via `Future.set_result` raising `InvalidStateError` on the second
  caller. Wrap the `set_result` in `McpPermissionServer.resolve` with a
  try/except and treat `InvalidStateError` as "already resolved" → return
  `False`. The first tap edits the message; the second's edit is a no-op
  via `contextlib.suppress(TelegramBadRequest)` (handler already does
  this).
- **Forged `choice` in `callback_data`.** The handler whitelists
  `choice in ("approve", "deny")` before calling `resolve_permission` and
  builds the decision dict on the *server* side based on that whitelist —
  the user's `callback_data` choice value never lands in the dict that
  goes to claude. This is stricter than CCR-009's approach (which read
  the choice from `_pending_options`), and safer: no need to keep options
  state in two places, the bot maps `approve | deny` to fixed dicts.
- **Malformed `callback_data`.** `_parse_callback` returns `None` →
  `"Stale prompt"` alert. Unchanged from the dormant scaffold.
- **`session_id` mismatch.** The handler's parsed `session_id` is
  ignored for the `resolve` call (the manager keys only on `request_id`).
  Why: the request_id is sufficient for uniqueness — it lives in a
  single global dict scoped to the manager, and a stale session's
  request_ids are forcibly cancelled in `_teardown_locked`. Keeping
  `session_id` in the callback_data is still useful for log debuggability
  and for future per-session UX.
- **Manager teardown while a permission is outstanding.**
  `_teardown_locked` calls `await mcp.cancel_pending(session_id)` BEFORE
  resetting `self._proc`. This resolves every outstanding Future for
  that session with a deny payload, which lets the MCP tool dispatch
  return cleanly to claude — claude's tool call sees the deny, claude
  emits a `tool_result` with the error, and the subprocess exits
  normally. If we did NOT cancel, the relay subprocess would be killed
  with a Future still awaiting and the subprocess's stdin/stdout pair
  would tear down underneath the SDK, possibly raising opaque errors in
  the asyncio loop. Belt-and-suspenders: `McpPermissionServer.stop` also
  cancels every pending Future on its way out.
- **Manager-side ordering.** The MCP server publishes
  `McpPermissionRequest` to the bus BEFORE awaiting the Future. Order:
  (1) mint `request_id`, (2) register Future in the dict, (3)
  `bus.publish("session.event", {"session_id", "seq": -1, "event":
  envelope})`, (4) `await Future`. The negative `seq` signals "synthetic,
  not in JSONL" so SSE-consumers do not double-bump their replay cursor;
  alternative: omit `seq` and have consumers tolerate `payload.get("seq")
  is None`. **Pick the omit-seq option** — it is one less
  mis-orderable thing. The broadcast loop already pulls `event` and
  `session_id` only.
- **JSONL log ordering invariant.** The CCR-007/CCR-009 invariant
  "log.append before bus.publish for every JSONL line" is preserved:
  `McpPermissionRequest` is NOT a JSONL line. It is a synthetic bus-only
  envelope. The log is untouched. Document this in
  `_consume_events`'s docstring AND in `McpPermissionServer._on_tool_call`
  to prevent a future change from accidentally trying to log it.
- **`McpPermissionServer.start()` errors.** If the relay subprocess
  fails to spawn (e.g. transport-script missing), `start()` raises a
  `McpServerStartError` with the original cause chained. `new_session`
  catches this the same way it catches `FileNotFoundError` for the
  claude binary and re-raises as a `SessionError` so the bot reports a
  clear message. Document this path; do not let it crash `serve()`.
- **Temp config file cleanup.** `McpPermissionServer.start()` writes
  `<data_dir>/.ccr-mcp-config.json` (deterministic path, NOT a tempfile,
  because claude's argv references it for the lifetime of the process).
  `stop()` removes the file. On crash the file is harmlessly stale and
  rewritten on next `serve()`.
- **Settings field naming.** `mcp_permission_timeout_seconds` matches
  the existing `subprocess_grace_kill_seconds` / `pairing_code_ttl_seconds`
  naming convention.
- **No DB schema changes.** The Future map is in-memory only.
  `Session.first_prompt`, `Session.last_event_at`, etc. are unchanged.
  No alembic migration in this ticket.

## Decisions

### In-process vs out-of-process

**In-process.** `McpPermissionServer` runs on the same asyncio loop as
the bot, web server, and `SessionManager`. Reasons: (1) `CLAUDE.md` is
explicit about "modular monolith on one asyncio loop"; (2) the server
needs synchronous read access to the bus and the Future map, which is
trivial in-process and a wire protocol out-of-process; (3) one fewer
subprocess to supervise; (4) the relay shim that bridges claude's stdio
to our in-process server is small and dies cleanly with the parent.

The relay shim is technically a child process (claude requires stdio
MCP servers as a command line; we point it at a tiny Python script that
forwards stdin/stdout to/from our in-process `Server` over a Unix
socket pair or a memory stream). The shim is NOT business logic — it is
purely transport. Treating the architecture as "in-process" remains
accurate: all the gating logic, all the Future bookkeeping, all the bus
publishes happen in the parent process.

### Transport: stdio vs TCP

**stdio.** Claude's `--permission-prompt-tool` flag and `--mcp-config`
config file documentation describe stdio MCP servers as the local
canonical case (e.g. `command: ["python", "..."]`,
`args: [...]`). TCP MCP servers exist but require additional
configuration (port, allowlist, cert if remote) we do not need. stdio
also matches the trust boundary — claude is already in our process tree;
the stdio bridge is the same lifetime as claude.

The `--mcp-config` JSON we write looks like (illustrative):

```json
{
  "mcpServers": {
    "ccr": {
      "command": "python",
      "args": ["-m", "ccr.claude.mcp_relay"]
    }
  }
}
```

…and `--permission-prompt-tool mcp__ccr__ccr_permission_prompt` follows
claude's documented `mcp__<server-name>__<tool-name>` resolution rule.
The relay (`ccr.claude.mcp_relay`) is a tiny `__main__`-style script
that opens a Unix socket / FIFO at a deterministic path under
`<data_dir>/` and proxies stdin↔socket and socket↔stdout. The parent
`McpPermissionServer` accepts the socket connection and runs the real
MCP `Server` against it.

**Open caveat:** the precise resolution of `mcp__ccr__ccr_permission_prompt`
(double underscore separator vs. single, server name "ccr" matching the
JSON key) is documented in Anthropic's MCP / Claude Code docs as the
default but the developer should sanity-check by searching the `mcp`
SDK's code or docs before settling the exact string. If the canonical
form turns out to be different (e.g. `mcp:ccr:ccr_permission_prompt`),
update the constant in `mcp.py` and adjust the `claude_argv` test.
**This is not a real-binary probe** — it is a docs/SDK lookup the
developer does without touching the claude binary. If the docs are
ambiguous and the developer cannot pin the form from public references,
they should escalate (a `BLOCKED` from the developer's chair, NOT
this architect).

### Future-keying scheme

**`request_id` is a manager-minted UUID4 hex prefix (16 chars).** The
MCP tool call arrives with `tool_name` and `tool_input` only — the SDK
does not provide a per-call id we can rely on (the `mcp` SDK assigns
JSON-RPC ids internally but they are not exposed to tool handlers in
all SDK versions). Minting our own id sidesteps SDK-version coupling
and keeps the `request_id` short enough to fit comfortably under
Telegram's 64-byte `callback_data` cap (`perm:` + 36-char UUID + 16-char
request_id + two `:` + `approve|deny` ≈ 67 — too tight; pick **8-char
hex prefix** of a UUID4 instead, total 60 bytes). The 8-hex prefix
collision space is `2**32`; with a few thousand outstanding requests in
practice the collision risk is negligible, and `register_request`
checks the dict for a collision and re-mints if hit.

### Timeout policy

**Default-deny on 120 s timeout.** On
`asyncio.TimeoutError` the MCP server resolves the Future internally
with `{"behavior": "deny", "message": "Timed out — no paired user
responded within 120s"}` and returns that to claude. Logged at WARN.
Configurable via `settings.mcp_permission_timeout_seconds` (1–3600).
Rationale: fail-closed is the safer default for a permission gate, and
a deny lets claude proceed gracefully (it sees the tool denied, emits a
`tool_result` with the error, and either re-prompts the user via
text or moves on).

The bot does NOT proactively edit the original message to "Timed out"
in this ticket — handling that requires a second bus publish path and a
second handler callback. Document as a follow-up. (Out of scope.)

### Concurrency

**Each request gets its own Future and its own Telegram message;
multiple permissions fan out in parallel without a global pause.** This
is a deliberate departure from CCR-009. With per-request Futures, the
"Telegram pause" CCR-009 introduced is unnecessary — every prompt has
its own keyboard and its own resolution path. Users can answer them in
any order. The broadcast loop simply renders each `McpPermissionRequest`
envelope as a regular outbound message (with keyboard) and moves on; no
buffer, no pause counter, no resume Event.

This also means the SSE side does not need any special handling either
— it just sees `McpPermissionRequest` envelopes interleaved with
`AssistantTurn` / `tool_use` events on the bus, in publish order.

### `--permission-prompt-tool` flag form

The exact CLI string is `--permission-prompt-tool mcp__ccr__ccr_permission_prompt`,
where:
- `mcp` indicates an MCP-resolved tool;
- `ccr` is the server name (matches the JSON key in
  `mcpServers.ccr`);
- `ccr_permission_prompt` is the tool name the server registers.

If the developer finds the documented separator differs (single
underscore, colon, slash), update the constant. The shape "name lookup
follows the MCP config" is canonical; only the punctuation might
differ. This is a docs/SDK lookup, not a binary probe.

### `ClaudeProcess.__init__` parameter — `mcp_argv` not a server reference

We pass a list of pre-built argv tokens, NOT a `McpPermissionServer`
instance. Reason: the process wrapper has no business knowing about
MCP; it just needs the argv. Keeps `ClaudeProcess` testable in isolation
(no need to spin up an MCP server in `test_claude_process.py` —
tests pass a hand-crafted token list). Mirrors how `resume: bool | str`
is also a flat data parameter rather than an object.

### Why `resolve_permission` returns `bool`

The handler needs to distinguish "successfully resolved" from "stale /
unknown" so it can pick the right Telegram alert. Returning a bool is
the simplest interface — no exception types to import, no enum to
extend. The two outcomes are exhaustive: either we set a Future that
was registered, or we did not. (Errors during the underlying `set_result`
call are caught inside `McpPermissionServer.resolve` and mapped to
`False`.)
